# Publishing: what each failure means and what to do

Read the reason the platform shows (the article's row on /pages, the Publish Error on /publish-calendar, or AI Chat), find it below, take the next step. Nothing here needs a retry-and-hope: a failure that retries by itself says so. In AI Chat, quote the reason, then use `release_publish_hold`, `unschedule_article`, `submit_approval` or `find_content` as the table says.

| Code or state | What it means | Next step |
|---|---|---|
| `no_rule` | Nothing is set up to edit this page on your site, so nothing was published. Add a page-source rule for it on the site connection, or publish it as a new article. | Account > Connections > your site connection: add a page-source rule, or publish it as a new article (/pages > Create publish PR). |
| `file_not_found` | The file behind this page was not found in your repository, so nothing was published. Check that the Destination URL is a live page, or publish it as a new page. | /pages > open the item > fix the Destination URL, then Create publish PR. |
| `record_not_found` | This address points at a data record that does not exist in your repository, so nothing was published. Set the Destination URL to the page you meant to revise, or publish it as a new page. | /pages > open the item > set the Destination URL to the page you meant, then Create publish PR. |
| `not_served` | No page on your site serves this address, so nothing was published. Publish it as a new page, or set the Destination URL to the page you meant to revise. | /pages > open the item > set the Destination URL, or publish it as a new page. |
| `repo_unreachable` | We couldn't reach your site's repository just now, so nothing was published. It will be retried automatically; if it keeps happening, check the GitHub connection. | None first: it retries by itself. If it repeats, reconnect GitHub in Account > Connections. |
| `guard_failed` | The edit would have changed more than the page's wording, so it was not published and nothing on your site changed. Try again, or apply the edit by hand from the manual-apply item. | /pages > Revise to redraft, or apply the edit by hand from its manual-apply item (Findings tab). |
| `llm_failed` | The writing model did not return a usable edit for this page, so nothing was published. Try again in a few minutes. | Wait a few minutes, then /pages > Revise. AI Chat: `submit_approval`, action revise. |
| `invalid_rule` | The page-source rule for this address is misconfigured, so nothing was published. Fix it on the site connection, then try again. | Account > Connections > your site connection: fix the page-source rule. |
| `adapter_error` | Publishing this page hit an unexpected error and nothing on your site changed. Try again; if it repeats, the details are on the Errors page. | Try again from /pages; if it repeats, the cause is on /errors. |
| `collision` | A page already exists at this address and it belongs to another article, so nothing was published. Give this article a new slug, or set its Published URL or Destination URL if it is meant to revise that page. | /pages > open the item > give it a new slug, or set its Destination URL if it should revise that page. |
| `truncated` | The writing model's output was truncated at its output limit twice, so nothing was published. Shorten the article or try again. | /pages > Revise with a note to shorten it. AI Chat: `submit_approval`, action revise. |
| `empty` | The writing model returned an empty response twice, so nothing was published. Try again in a few minutes. | Wait a few minutes, then /pages > Revise. |
| `unchanged` | The update for this page changed none of its copy, so nothing was published and no pull request was opened. Try again; if it repeats, the approved edits may sit outside the parts of the page the site lets us edit, so apply them by hand. | Open the article and confirm the approved edit is in it, then /pages > Revise; if it repeats, apply the edit to the page by hand. |
| `held:needs re-review` | The publish PR changes more than expected, so the calendar will not merge it. | /pages > open the item > read the diff > "Publish anyway", only if it is fine. AI Chat: explain what was flagged, then `release_publish_hold`. Not fine: Revise. |
| `held:site build failed — reverted` | The site build failed after the merge and the platform reverted the change. The page is back as it was. | Open the revert PR from the notice, fix what broke the build, then /pages > Revise and publish again. |
| `CI failed: <check>` (PR not merged) | A check on the publish PR is red; the check is named. A failing "Cloudflare Pages" check means its build failed. | Open the PR, open the named check's log, fix it. Publish repair tries twice by itself. Then Publish live (or Reschedule on /publish-calendar). |
| `waiting for CI` / `CI never finished` | Checks are still running. The calendar waits (about 3 hours) then fails. | None while it waits. After it fails, open the PR and look at the stuck check, then Reschedule. |
| `site build failed: Cloudflare Pages / Vercel / Netlify reports ...` | The PR merged but the host's build of that merge failed, so the page will not appear. | Open the build log link in the message, fix the build, then /pages > Publish live again (the row is still awaiting its URL). |
| `merged but the URL never resolved` | The PR merged but the page was never found at the expected address. | Open the site, find the page, then submit its URL on the item (Awaiting Live URL panel). |
| `WordPress ... did not load` / `reading it back failed` | WordPress took the post but we could not confirm it is live. The row stays Approved and keeps its post id. | /pages > Publish to WordPress again: it updates the same post. |
| `merge failed` | GitHub refused the merge. | Open the PR, resolve the conflict or failing review, then Reschedule. |
